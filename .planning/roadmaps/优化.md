# RAG 项目优化清单（2026 年中视角）

> 生成日期：2026-06-01
> 基于当前 CLAUDE.md / hot cache / ADR 实现状态分析，按 ROI 与改造成本排序。

## 一、立即可做（不需要新基建，主要补齐 / 落地未完成的）

### 1. 先把 BM25 build 跑起来 ⚠️ 已投入未收回
- **背景**：`MdKeywordSearchServiceImpl` 已升级 BM25（adr-013），但 `db/manual/md-bm25-build.sql` 未跑，`tokenizer_catalog.model/text_analyzer/tokenizer` 三表 0 行，`md_model` 不存在，运行时仍走 TRGM
- **动作**：语料 ingest 后手动跑 build 脚本，验证 BM25 链路真正可用
- **收益**：把已写的代码变成线上收益，沉没成本翻正
- **优先级**：P0

### 2. Contextual Retrieval（Anthropic 2024.09）⭐ 最高 ROI
- **背景**：对每个 child chunk，embed 前用 LLM 生成「这段文字在整篇文档里的语境」前缀（50-100 token），再 embed + BM25 索引
- **官方数据**：retrieval failure 降 35%（contextual embeddings）/ 49%（+ contextual BM25）/ 67%（+ rerank）
- **适配性**：你们结构天然契合 —— parent 整段 section 是现成的 context 来源，让 LLM 看着 parent 给 child 生成语境前缀，写到 `md_child_chunk.embed_text` 即可
- **改动面**：ingest 管线一处（`MarkdownStructureIngestionService` / `MdVectorStoreService`），不动检索侧
- **优先级**：P0

### 3. 真正的 evaluation 闭环（RAGAS 或自建）
- **背景**：ADR-014 评估侧已立中立立场，但 md RAG 检索/答案侧没有自动化评测；intent-routing 的 `DomainRouterEvalTest` 是孤例
- **动作**：
  - 收 50-200 条人工标注 `(question, golden_chunk_ids, ideal_answer)`
  - 指标：context recall / precision @ K、faithfulness、answer relevance
  - 接 CI 或 nightly 跑，挂 LangFuse 看趋势
- **价值**：没有评测，下面任何「优化」都只是感觉，不是事实
- **优先级**：P0

### 4. LangFuse tracing 起栈联调
- **背景**：ADR-015 代码已落地编译通过，运行态未验证（span 树渲染、prompt/completion event→attribute 映射、跨线程传播实测全待联调）
- **动作**：`docker compose --profile tracing up -d`，跑端到端、验证 span 树
- **价值**：评测闭环的线上数据来源
- **优先级**：P0

## 二、中等改造（需要写代码，架构不变）

### 5. Self-RAG / Corrective RAG（CRAG）
- 在 ReactAgent 内加一步**自我评估**工具：检索后让模型判断 chunks 是否足够；不够 → 触发 query 改写后重检索；矛盾 → 显式标注分歧
- 改动：ReactAgent 多一个 `evaluateRetrieval` 工具，不需要新框架
- 优先级：P1

### 6. Late Chunking（Jina 2024）
- 先整篇 embed（需 long-context embed 模型，如 `jina-embeddings-v3` 8192 token）→ 按 token 边界切 embedding，每个 chunk embedding 都「见过」全文
- DashScope embedding 上下文 8K，可尝试
- **代价**：换 embed → `md_kb_chunks` 重建 + 全量重 ingest（CLAUDE.md 已警告），成本不低
- 优先级：P2（需先做 #3 评测对比）

### 7. Query 复杂度路由 + 多跳查询分解
- 入口加轻量分类器（可复用 `DomainRouterService` 两层架构思路）：
  - simple lookup → hybrid search + parent expansion
  - multi-hop / 比较类 → LLM 拆子问题，分别检索后聚合
  - 复杂任务 → ReactAgent
- 优先级：P1

### 8. Reranker 升级
- 候选：Cohere rerank-3.5（多语言强）/ bge-reranker-v2-m3 / Qwen3-Reranker-8B（开源可自部署）/ ColBERT-style late interaction
- 切换点：`RerankService` 单点替换；**必须先做 #3 评测对比**，不要凭感觉换
- 优先级：P2

### 9. 缓存层
- **Embedding cache**：query 文本 hash → 向量，Redis TTL
- **Retrieval cache**：query + spaceId hash → topK chunk ids，TTL 5-15 min
- 防热点查询击穿 Milvus
- 优先级：P1

## 三、需要新模块 / 新基建

### 10. GraphRAG / 实体关系层
- **历史**：曾有 `kb-knowledge-graph` 模块，随标准 RAG 退役删除
- **趋势**：2024-2025 Microsoft GraphRAG、LightRAG、HippoRAG 2 把「实体抽取 + 社区检测 + 子图召回」打成相对标准范式
- **价值**：跨文档 / 跨章节聚合（"X 公司 2024 年所有事件"）、全局摘要类问题（纯 vector 拿不到）
- **建议**：若重新引入，**明确只解决跨文档/全局问题**这一窄场景；LightRAG 比 MS GraphRAG 轻量，先试
- 优先级：P2

### 11. 真正的视觉 RAG（替换 Noop）📌 MEMORY 已标 Noop
- **现状**：视觉管线搭通但不支持真正图片信息检索
- **2024-2025 进展**：
  - ColPali / ColQwen2：把页面截图当 patch 序列 embed，跳过 OCR → 解析 → 重排版传统管线，对 PDF / 含图表 markdown 收益巨大
  - 已有 DashScope = 直接用 Qwen-VL 做 image understanding（不止占位）
  - Milvus 已支持 multi-vector，存 patch embeddings 不用换基建
- **代价**：ColPali 类方案 embedding 维度暴涨（每页几百个 128-dim vector），存储/检索成本上去
- 优先级：P2（先评估需求）

### 12. 结构化数据 / 表格 RAG
- 现状：表格"双表示"（线性化检索 + 原始返回），复杂表格问答（聚合、对比、计算）走不通
- 方案：
  - 表格抽出后转临时 SQLite，ReactAgent 加 `queryTable` 工具
  - 或用 Qwen2.5-Coder 类小模型做 NL→SQL
- 优先级：P2

### 13. Long-context fallback
- 当 retrieval 召回 chunks 总长 < 上下文窗口 30%，且置信度不高时，**直接把整篇 parent 文档塞进 prompt**
- Claude 4.x / Qwen Long 200K+ 上下文够用
- 哲学：retrieval 是为了「省钱省延迟」，不是目的本身
- 优先级：P2

## 四、产品 / UX 层（被低估）

### 14. Citation 高亮 + 来源可点击
- 问答返回了 chunk，但前端是否真渲染了「这句话来自第 X 节」？用户信任的核心
- 优先级：P1

### 15. Confidence 显示 + Disagreement detection
- 不同 chunks 给出矛盾信息时，显式标出「两个来源说法不一致」
- 比硬选一个更负责
- 优先级：P2

### 16. Follow-up 问题生成
- 答完后让模型生成 3 个相关问题，引导深挖
- 低成本高粘性
- 优先级：P2
